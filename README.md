# 재고이동 레이더 (Inventory Movement Radar)

매장 간 재고이동이 필요한 SKU, 그리고 창고(중앙 물류)에 발주해야 할 SKU를 찾아주는
도구입니다. 세 방향을 지원합니다.

- **받을 재고** — 우리 매장은 잘 나가는데, 다른 매장엔 잠자고 있는 재고 찾기
- **보낼 재고** — 우리 매장엔 잠자고 있는데, 다른 매장에서 잘 나가는 재고 찾기
- **물류주문** — 창고엔 재고가 넉넉한데 우리 매장에서 잘 팔리는 상품 찾기 (지점간 이동이 아니라
  창고에 바로 발주해야 할 후보)

`index.html` 파일 하나로 동작하는 정적 페이지이며, 데이터는 이미 파일 안에 담겨 있어
여는 즉시 바로 쓸 수 있습니다.

## 사용 방법

1. 아래 GitHub Pages 주소(또는 `index.html`을 직접 열어서) 접속
2. 사이드바 상단에서 **받을 재고 / 보낼 재고 / 물류주문** 중 방향을 선택
3. 왼쪽 사이드바에서 **내 매장**을 선택
4. 표에 뜨는 특이 SKU 확인
   - 받을 재고 모드: "판매없음"은 즉시 이관 후보, "판매부족"은 검토 대상
   - 보낼 재고 모드: "체화재고"는 즉시 이관 후보, "판매열세"는 검토 대상
   - 물류주문 모드: "재고소진"은 매장 재고가 이미 0인 즉시 발주 대상, "주문검토"는 아직 재고는
     있지만 판매가 활발해 미리 발주를 검토해볼 대상
5. 필요하면 브랜드·카테고리·판매(재고) 상위 개수, 창고재고 기준 등 조건을 조정
   (기본값: 창고에 100족 이상 있는 SKU는 받을 재고·보낼 재고 후보에서는 자동 제외되고, 대신
   물류주문 모드의 후보로 잡힙니다)

별도 설치나 로그인이 필요 없고, 파일을 새로 올릴 필요도 없습니다.

### "물류주문" 모드는 무엇을 보여주나요

받을 재고·보낼 재고 모드는 둘 다 "창고에 100족 이상 있으면 그 SKU는 후보에서 제외"합니다 —
창고에서 바로 보충하면 되니 지점간 이동은 불필요하다고 보기 때문입니다. 그런데 그렇게 제외된
SKU 중에는 **우리 매장에서 유독 잘 팔리는 상품**이 섞여 있을 수 있고, 이런 상품은 지점간 이동이
아니라 **창고에 발주하는 액션**이 필요합니다. "물류주문" 모드는 정확히 이 교집합만 따로 뽑아
보여줍니다: 우리 매장 판매 상위 SKU 중, 창고재고가 기준(기본 100족) 이상인 것들. 사이드바의
"창고재고 최소 기준" 슬라이더로 그 기준을, "우리 매장 판매 상위" 슬라이더로 몇 개까지 볼지
조정할 수 있습니다.

## GitHub Pages 주소 확인/설정

저장소 **Settings → Pages**에서 Source를 `Deploy from a branch` → 브랜치 `main` / `/ (root)`로
설정하면 몇 분 뒤 `https://<깃허브아이디>.github.io/<저장소이름>/` 주소가 활성화됩니다. 그 화면
위쪽에 뜨는 "Your site is live at ..." 링크가 실제 접속 주소예요. 이 링크는 인터넷에 공개되는
주소이니, 링크 공유 범위에 유의해주세요.

### 검색엔진 색인 차단

이 페이지가 구글 등 검색 결과에 노출되지 않도록 두 가지 조치를 해뒀습니다.

- `index.html`의 `<head>`에 `<meta name="robots" content="noindex, nofollow">` 삽입
- 저장소 루트에 `robots.txt` 추가 (`index.html`과 같은 위치, 즉 저장소 최상위 폴더에 올려야
  `https://<깃허브아이디>.github.io/<저장소이름>/robots.txt`로 인식됩니다)

다만 이건 검색 결과에만 안 뜨게 하는 것으로, 링크 자체를 아는 사람은 여전히 누구나 접속할 수
있습니다. 완전한 접근 제한(비밀번호 등)이 아니라는 점을 유의하세요.

## 데이터 최신화 (관리자용)

이 페이지에 들어있는 데이터는 특정 시점의 스냅샷입니다. 최신 데이터로 갱신하려면:

1. 최신 엑셀 5종(가격표, 점별판매현황, 점별재고, 창고재고, 입고일)을 준비
2. 그 파일들을 Claude에게 전달해 새 `index.html`을 요청
3. 받은 파일로 이 저장소의 `index.html`을 덮어쓰기(같은 파일명으로 재업로드)

일반 사용자는 이 과정을 몰라도 되고, 페이지에는 업로드 화면이 따로 없습니다 — 관리자가 위 과정을
거쳐 갱신한 스냅샷을 그대로 보게 됩니다.

### 덮어쓰기가 실제로 반영됐는지 확인하는 법

사이드바 제목 바로 아래에 옅은 뱃지로 **"페이지 버전"**과 **"데이터 기준"** 시각이 항상 떠 있습니다.
파일을 새로 덮어쓴 뒤 이 값이 Claude가 알려준 최신 시각과 같으면 정상 반영된 것이고, 그대로라면
아래 순서로 확인하세요.

1. GitHub 저장소의 `index.html` 파일 용량이 바뀌었는지 확인 (파일 목록에서 바로 보입니다)
2. Settings → Pages에서 최근 배포(deployment)가 방금 커밋 이후로 완료됐는지 확인 (보통 1~2분)
3. 그래도 뱃지 값이 안 바뀌면 브라우저 캐시 문제 — 강력 새로고침(Ctrl/Cmd+Shift+R) 또는
   시크릿 창으로 다시 열어보세요.
